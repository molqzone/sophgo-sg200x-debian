# shared-page-xr 重构方案：rpmsg 兼容契约

## 1. 背景与目标

**为什么重构**：目标是把 Linux 的 remoteproc/rpmsg 生态复用起来——自定义 rpmsg transport 读同一张共享页即可获得 `/dev/rpmsgN`、端点 API、按名发现。前提是**页面报文按 rpmsg 协议来**（帧格式 + 命名通道语义），传输层保持 mailbox-only（无资源表、无 vring、固定地址不变）。

**上游决策（权威来源）**：origin issue #6《共享页采用 rpmsg 帧与名称服务、cmdqu 保持为门铃；并修复 C906L→Linux 的 mailbox 中断》已定型架构——只取 rpmsg 的帧 + 命名两层（`rpmsg_hdr`/`rpmsg_ns_msg` 线格式 + 页内名称表自实现 NS 语义），**明确不采用 virtqueue/vring**（会要求资源表、绕回全量 rpmsg、且丢掉页面的 keep-latest/claim 语义）。本计划是该决策在本仓库的落地细化；两者冲突时以 issue 的线格式为准，本计划的命名/布局细化属于增量。

**范围界定**：

- 本仓库负责：契约规格文档 + 本仓库消费方（`guidance-cmd.py`、`bootlogd`）
- 固件仓库（`bsp-guidance-action`：shared-page-xr / `guidance_contract.hpp` / `sg200x_console.hpp`）按规格实现，本仓库不修改
- 相机环（`0x8ffde000`，`sg2002-camera-bridge` 所属）是独立契约，本方案只登记不改

**非目标**：不引入资源表/virtio；不改变固定物理地址；不改变门铃传输；不改相机环格式。

## 2. guidance-cmd 是什么（重构的主要对象）

`components/guidance-fw/tools/guidance-cmd.py`（板上 root 运行）是 **Linux 侧操作 C906L 的唯一控制面工具**，经共享页 + CMDQU 门铃通信。子命令：

- `format`：按当前常量初始化共享页头
- `ping` / `led on|off` / `park`：发命令（GMD1 帧：magic/kind/seq/16B 数据），等门铃回复
- `status`：dump 页头、NS 主题表、region seq/state、最后一条命令、mailbox 8 个 slot 状态
- `log [--new]`：流式读固件 console 页（0x8FFDB000，write_index + 4032B ring），带 overrun 检测
- `restart`：park → remoteproc stop/start 循环（直接 reset 会因总线主控挂住共享 AXI fabric、打死 USB 网络，所以先 park）

内部结构：

- `Page`：`/dev/mem` mmap 一页（4KB），read/write/u32 助手
- `Mailbox`：CMDQU 块（0x01900000）视图，8 个 context slot（0x01900400 起，8B/个：ip / cmd|block / resv=linux_valid|rtos_valid / param）；`clear_slot`、`drop_stale_replies` 回收残留回复槽
- 发布协议：写 payload → 写 region seq 释放（`write_command`）；`next_seq()` 保持 16bit slot seq 与 32bit region 计数同步
- 门铃**只有一条路**：`/dev/cvi-rtos-cmdqu` 的 `RTOS_CMDQU_SEND_WAIT`（内核等待表，事件驱动）。现有的裸写寄存器 + `poll_reply` 轮询路径是 IRQ 损坏期的临时产物，**重构时删除，不作为回退保留**——设备缺失是硬错误（`/proc/interrupts` PLIC 101 不涨同样是硬错误），不是降级理由
- `ns_entries`：读页内 NS 表（LibXR Topic 名 + crc32 + 地址 + flags）

它是本契约的**唯一重度消费方**：页头全部 8 个字段、NS 表、命令区发布协议、console 页格式，都在它以常量形式手抄了一份（`SHARED_PAGE_PHYS` / `NS_OFFSET` / `WIRE_TAG` / `CMD_MAGIC` …）。契约漂移首先在这里体现为静默错位——这是重构要把布局收敛进规格文档的直接原因。

## 3. 现状盘点（重构的实证依据）

共享页 `0x8FFDC000`（4 KiB）当前实际布局（从消费方代码反推）：

| 偏移 | 内容 | 消费方 |
|---|---|---|
| 0x0000–0x0020 | PageHeader（8×u32：magic/abi/page_size/slots=60/sample=64/payload=24/region=4064/wire_tag=4） | guidance-cmd.py |
| 0x0020–0x0F28 | 60 个 framed slot（`rpmsg_hdr` 16B + Sample 48B，遥测发布区） | 固件发布 |
| 0x0A20–0x0FDC | **1460B ring**（write_index@2600、telemetry_head@2592、bytes@2604） | bootlogd |
| 0x0F28–0x0FE0 | NS 表（16B 头 + 最多 4 条 42B 记录：crc/addr/flags/name_len/name[28]） | guidance-cmd.py status |
| 0x0FE0–0x1000 | Command Region（24B GMD1 命令 + write_state@4088 + seq@4092） | guidance-cmd.py |

**设备树侧事实**（`configs/maixcam/dts/cv181x_licheervnano_sd.dts`，2026-10 现状）：

- `fast_image` 收窄为只含固件镜像（`RTOS_FIRMWARE_SIZE`，到 0x8FFDE000 为止）；相机环（`rtos_shm` 132KB）与 boot trace 单独声明
- C906L 独享的总线在 Linux 侧全部 disabled：DMAC（C906L SPI/IMU 的唯一 DMA，双核探测会挂 SoC）、SPI2（**IMU 总线，C906L 唯一 SPI 客户**）、SDIO1（**ESP32-C5 slave，C906 做 host**，属 bring-up 镜像）
- 三个 vring 节点被 `/delete-node/` 直接删除（vendor RPMsg 设计痕迹清空）
- 相机环同时登记在 `rtos_cmdqu` 节点的第二个 reg（`"shared-memory"`）名下——vendor 共享内存 IPC 栈已退役（guidance README），该区域目前只服务于 bring-up 期的相机桥
- `tools/maixcam-camera/README.md` 的数据通路描述（"C906L SPI2 -> ESP32-C5"）与 DTS（SDIO1）不符，是文档漂移

**已发现的契约病灶**（不是风格问题，是实际缺陷）：
1. **ring 与 slot 数组重叠**：ring 占 2604–4064，slot 数组占 32–3872，重叠约 1268B。header 里 `slots=60` 与实际可用数不符——要么固件少用尾部 slot，要么 bootlogd 读到的是遥测数据当 console。必须二选一并文档化。
2. **console 有两个家**：`guidance-cmd.py log` 读独立 console 页 `0x8FFDB000`（4032B ring，`Core/sg200x_console.hpp`）；bootlogd 注释却写 "console ring 在共享页 +2604"。至少一方是错的，而 bootlogd 是挂死后唯一的取证手段——读错地方 = 取证失效。
3. **NS 区几何与注释不符**：注释称 "60 framed slots + head/write_state"，实际 3880–4064 只放得下 4 条记录（代码 `min(count,4)` 已承认）。60 是 slot 数组的数，不是 NS 的数。
4. **命令区仍是自定义帧**（GMD1 magic），而 NS slot 已经用上 `rpmsg_hdr`——迁移做了一半，两套帧并存。
5. **契约无单一来源**：偏移量散落在 `guidance-cmd.py` 常量、bootlogd 内嵌 python、README 一句话、固件三个头文件，改任何一处不会在别处报错。

## 4. 目标契约设计

### 4.1 通道模型

页面表达为一个 rpmsg 设备，下属命名通道（名字 ≤ 32 字符，rpmsg 语义）：

| 通道 | 方向 | 载体 | 帧 |
|---|---|---|---|
| `guidance-cmd` | Linux→C906L 请求 / 回复 | Command Region + mailbox 回复 | `rpmsg_hdr` + GMD1 负载 |
| `telemetry` | C906L→Linux 发布 | 60 framed slots（区号显式声明） | `rpmsg_hdr` + Sample（保持现状） |

> 注： framed slot 的 Sample 即 BMI088 IMU 遥测（SPI2 是 C906L 唯一 SPI 客户）。本仓库目前**没有遥测消费方**——`guidance-cmd.py status` 只列 NS 主题名，没人读 slot 数据。重构后此通道保持原名新格式，消费方（IMU 读取工具）作为独立需求另立。
| `console` | C906L→Linux 流 | 独立 console 页 `0x8FFDB000`（4032B ring） | 流式，消费时分块 |
| `maint` | C906L→Linux 调试流 | 页内 ring（**二选一后保留的一个**） | 流式，含 PLIC dump |

通道表只登记**当前存在的服务**；新通道由固件经 NS 通告时按命名规则取名，不在规格里预占。

> 注 1：framed slot 的 Sample 即 BMI088 IMU 遥测（SPI2 是 C906L 唯一 SPI 客户）。本仓库目前**没有遥测消费方**——`guidance-cmd.py status` 只列 NS 主题名，无人读 slot 数据。重构保持原名新格式，IMU 读取工具作为独立需求另立。
>
> 注 2：相机数据链路在 Linux 侧闭环（VI/VPSS/VENC），C906L 不再经手视频；若将来需要把位置数字送进 C906L（转发 C5 或别的用途），按数据性质是**小消息通道**，走页内 framed slot 即可——**不是** 132KB 相机环（见 §8 决策项）。

**命名与寻址原则**（本契约的核心）：

- **名字字符串的职能是页内索引**：name →（地址、尺寸、格式）。因此命名空间归索引的 owner——**LibXR**；产品代号（guidance / GMD1）不是线序契约的一部分，是迁移残留，随重构清除
- **页内固定的只有两样**：PageHeader + NS 索引表。命令区、console 页、maint ring、framed slots 全部经 NS 按名发现；消费方不持有任何硬编码偏移（`guidance-cmd.py` 现有常量体系随之废除）
- 通道名不含核名前缀（核身份由 rpmsg 设备/总线隐含携带）；vendor 侧被驱动匹配的标识（`cv181x-c906_1` compatible）不在此列
- **全链路禁止轮询退路**（用户明确要求，与 shared-page-xr 信条一致）：门铃走 `RTOS_CMDQU_SEND_WAIT` 事件驱动；transport RX 走 mailbox IRQ；页消费走 `WaitAndPublish` 事件信号量。IRQ 不涨/设备缺失/冷页都是**硬错误**，就地报错，不提供 polling 降级——轮询一旦存在就会因“方便”变成实际使用的那条
- 上表通道名为语义占位，定稿遵循 LibXR topic 命名约定（见 §8 开放问题）

**与 issue #6 的命名差异（需回帖对齐）**：issue 示例用的是 `c906-console`、`camera-pos`——带核名前缀、且预占了假想通道，与本计划的命名原则（无核名前缀、只登记现存服务）相反。建议在 issue 下回帖修正，避免规格分裂。

**帧与槽的关系（issue #6 明确）**：帧只作为**槽内载荷**，`head`/claim 的“保留最新、无分配”协议继续负责槽的生命周期——**不要用帧替代 head**。遥测槽 = `rpmsg_hdr`(16) + payload(48) = 64B。
回复路径保持 mailbox（IRQ 修好后 `RTOS_CMDQU_SEND_WAIT` 已可用）；页内回复 slot 作为 v2 选项登记进文档。

### 4.2 帧格式（消息通道）

Command Region（offset 4064，32B）新布局：

```
rpmsg_hdr:  src=0(Linux) dst=CMD_ADDR reserved=0 len=24 flags=0     (16B)
payload:    GMD1 magic | kind:u16 | seq:u16 | data[16]               (24B 原样保留)
release:    write_state@4088, seq@4092（发布协议不变）
```

即**负载格式零变化**，只外包一层 `rpmsg_hdr`——固件改动最小，而报文从此可被标准 rpmsg 解析器直读。NS 记录采用 `rpmsg_ns_msg` 兼容核 + 厂商扩展（字段顺序以内核 `include/linux/rpmsg.h` 和 issue #6 为准——**name 在前**）：

```
struct rpmsg_ns_msg { char name[32]; __le32 addr; __le32 flags; }   /* 40 B，标准核 */
厂商扩展（紧随其后）：u32 gen; u32 crc                             /* +8 B = 48 B/条 */
```

- 端点地址是 **u32**；`RPMSG_NS_ADDR = 53`，NS 通告本身是普通帧（`dst = 53`），“帧 + NS”自洽
- NS 表容量 4→8 条（16B 头 + 8×48B = 400B，置于 3880–4064 区间；若与 Command Region 争空间则 NS 表迁至头区后的保留带，**精确算术由规格文档定案**——issue #6 的布局草图按 63 槽估算时未计入名称表，两者必须调和）

### 4.3 布局重叠的裁决

**裁决：页内 ring（2604–4064）与 framed slot 数组不共存。** 推荐方案：slot 数组缩为 40 个（32–2592，遥测够用），2592 起为 maint ring（telemetry_head@2592 / write_index@2600 / bytes@2604，大小 1460B 至 4064）。header `slots` 字段改为 40 并新增 `maint_ring_off/size` 字段。console 明确归独立页，bootlogd 改为读 `console` 页 + maint ring 两者都快照（挂死取证两个都有用）。

### 4.4 版本与 fail-fast

- `wire_tag` 4→5，`abi` 1→2；`guidance-cmd.py` 与 bootlogd 启动即校验，不匹配**拒绝运行并打印实际 header**（现状 `page_ready()` 已有此形，扩展为全部字段含新字段）。
- 过渡期双接受：Command Region 同时接受旧 GMD1（无头）与新 rpmsg_hdr 帧，按 header 的 feature flag 判定，window 内之后删除旧路径。

## 7. 验证计划

**mailbox IRQ 状态（issue #6 已闭环）**：根因是固件 `Reply()` 写 bank 0（vendor 头文件把 0 命名成 “ca53”），而 SG2002 上 Linux 大核收 bank 1。固件改为 `SEND_TO_LINUX = 1` 后：`/proc/interrupts` PLIC 101 每条命令 +1，`RTOS_CMDQU_SEND_WAIT` 由内核 wait list 唤醒、不再轮询；此前那个 `RECEIVE_CPU 0` 内核补丁是错的，已回退未进镜像。**含义**：自定义 transport 的 RX 从第一天起就是事件驱动——**全链路禁止轮询退路**（与 shared-page-xr 的信条一致：轮询一旦存在就会因“方便”变成实际使用的那条，事件路径随之烂掉）。IRQ 不涨 = 硬错误，就地报错，不降级。

1. **契约自测**（新增 `--selftest`）：格式化→header 校验→NS 读取→命令往返→console 流读取，全过才退出 02. **fail-fast 测试**：手工把 wire_tag 改错，确认工具拒绝运行且打印实际值
3. **板级回归**：`ping/led on/led off/log --new/park/restart` 全过；`bootlogd` 跑一个 15s 周期确认快照有 console 内容
4. **相机路径无回归**：相机环未动，`razver-camera.service` 行为不变（板子恢复后验证）
5. **IRQ 修复后验证**：issue #6 已确认闭环（固件 bank 1，`/proc/interrupts` PLIC 101 随命令 +1，`SEND_WAIT` 不再轮询）——板级验证时复核一次即可
6. **固件改动后的重启方式**：issue #6 实测——`park → stop → start` 原地重启 rproc 会让 BMI088 加计读回恒定 0（陀螺正常，冷启动正常），根因在固件加计初始化状态未恢复。**验证固件改动必须整板 reboot，不要 rproc 原地重启**（`deploy_rtos_fw.sh` 已改为 park → stop → 装 ELF → reboot）
前置依赖：板子当前 degraded（相机管线崩、SSH 拒连），板级验证需等板子恢复；串口可用。

## 8. 风险与开放问题

1. **最大风险是固件侧不在本仓库**：规格再精确，实现排期取决于固件仓库；缓解手段是规格文档含逐字节布局表 + 自测工具，固件侧可对照自验证
2. **NS 表容量**：4→8 条若与 Command Region 争空间，需重新划分（方案给的口径：不够就把 NS 表移进头区后的保留带，规格文档定案）
3. **双接受窗口**：旧 GMD1 直读路径删除时机需和固件发版对齐，建议一个镜像版本
4. **相机环去留（新决策项）**：C906L SPI 已只剩 IMU、视频链路 Linux 侧闭环、vendor IPC 栈已退役——132KB 相机环（`rtos_shm` + `rtos_cmdqu` 第二 reg）目前只服务 bring-up 期相机桥。选项：(a) 保留原样（bring-up 变体还要用）；(b) 退役（删 DT 两处声明，132KB 还给固件/内核）；(c) 缩水重定位为小消息通道区。建议 (a) 过渡 + 在规格文档登记，待 bring-up 收尾后执行 (b)
5. **bootlogd 取证连续性**：改读取位置后，历史 snap.log 的格式语义变化需在 00-marker 注明，避免新旧混读误判
6. **guidance 命名空间清除范围（新决策项）**：线序契约内清除已定（GMD1 magic、`guidance::` 常量、NS 名归 LibXR）。仓库侧是否跟着改——`components/guidance-fw/`、`guidance-cmd.py`、`c906-ready.service`、`ENABLE_GUIDANCE_FW` 等文件名/开关名——需要决策：只清契约（零风险）还是连仓库命名一起清（涉及 Makefile 开关、systemd 单元、README 全链）。建议分两步：先契约，仓库命名待固件侧新命名空间定稿后统一改
